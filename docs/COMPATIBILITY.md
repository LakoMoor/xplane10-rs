## Measured format facts that contradict the pre-existing evidence ledger
- **E-0012 described `TRIS <count>` as opening a block whose `IDX10` lines follow it, and
  `POINT_COUNTS` field 4 as a triangle count.** In shipped content the index stream precedes the
  descriptors and field 4 counts indices: `fuse.obj` holds 10 944 indices (3 648 triangles) and
  its three `TRIS` lines sum to exactly 10 944. The parser follows the file, not the ledger.
- **`VLINE x y z r g b` is a line-vertex directive**, counted by `POINT_COUNTS` field 2 — not a
  block header. It looked like one because the index stream begins right after the last `VLINE`.
- **`TEXTURE` with no argument is legal**: 82 shipped objects are placeholders that pair an empty
  `TEXTURE` with `POINT_COUNTS 0 0 0 0` and an `EXPORT` redirect.
- **`#`-prefixed lines are WorldEditor metadata** (`####_group`, `####_alpha`, `# Image: …`),
  kept verbatim in `Obj8::metadata_lines`; OBJ8's own comment character is `*`.
- **apt.dat has no indentation at all** (7 155/7 155 KSEA lines start at column 0), so any parser
  that assumes indentation-based nesting cannot read these files.
- **`POINT_COUNTS` field 4 counts the whole index stream — including the positions `LINES`
  consumes — while field 2 counts line *vertices*.** `balloon3.obj` declares 48 line vertices but
  its `LINES` descriptors cover 60 indices. Comparing field 4 against the sum of `TRIS` counts
  alone flags 73 structurally sound shipped objects as broken.
- **Draw descriptors need not appear in stream order.** `UtilityShed1.obj` declares
  `TRIS 138 6`, `TRIS 0 138`, `TRIS 144 54` in that order and tiles `[0, 198)` exactly.
- **19 of the 59 shipped `.acf` files are not text ACF at all**, so "acf malformed" was the wrong
  label for them: they are a separate serialization, detected but not modeled.

## Known ledger discrepancies and open unknowns
- E-0009 recorded "913 distinct normalized key shapes / 888 distinct `acf/*` leaves" for the
  C172SP. Measuring the same file with two explicit rules gives 4 897 (digits-only-segment) and
  1 435 (per-comma-component). The golden now pins the rule the port implements; E-0009's
  numbers are not reproducible with a stated rule and are treated as superseded, not as a target.
- The QA-script time base (wall vs sim clock) is unresolved, so frame-indexed state goldens are
  not yet trustworthy.
- DSF chunk *semantics* are unrecovered; only framing is measured. The original's own error
  string implies 8-character cookies, which does not match the 4-character tags observed, so the
  chunk model is still partly unknown.

- **`--load_acf` is accepted but not honored.** The oracle was run with
  `--load_acf=…/StinsonL5/L5.acf` and with `--load_acf=…/Death-Trap.acf`; its own Cycle Dump
  reported `Simulating Aircraft/General Aviation/Cessna 172SP/Cessna_172SP.acf` both times, and
  `I/ACF: Loading airplane number 0…3` lists C172SP, KingAir C90B, C-130 and Columbia-400. The
  goldens therefore cover only the built-in default aircraft, and **whether the original loads
  the 19 legacy binary ACFs is still unmeasured** — this port detects them and does not model them.
- **The oracle does not terminate under `--qa_script`.** Runs reach `Simulating …` (the Cycle
  Dump written on kill proves it) but keep running past the script's `quit`, so they have to be
  killed externally. Log.txt stops at 6 552–6 650 bytes, before the aircraft- and
  scenery-load sections the goldens would need.
- **REA could not analyze the oracle in the time it allows.** `search_strings`, `xrefs` and
  `procedure_pseudo_code` each ended in `provider_timeout` (330 s) on the 53 MB Mach-O on
  2026-11-10. The binary keeps its symbol table, so the GPS-database slice was recovered with
  `nm` + `llvm-objdump` and the scripts in `tests/original_patch/re/`. No decompiler output
  backs these rows; they rest on annotated disassembly read by hand.
- **`IO_apt` itself is not ported.** `xp_core::gpsdb` reads only the airport headers and the
  `100`/`101` records and reproduces the airport table by first-identifier-wins. The original's
  reader (`0x1006ca340`, 12 000 instructions) also has a `Global Airports` special case, an
  `IO_apt_fix_broken` pass and its own decimal scanner (`xmap_class::TXT_dob_scan`); none of the
  three changes the count on this install, and none is measured beyond that.
- **`aptdat::AptDat` recognises only the `1` header.** `16` (seaplane base) and `17` (heliport)
  records do not start a new airport there, so their runways and pads are attached to the land
  airport before them, and `Airport::name()` returns the identifier glued to the name
  (`KSEA Seattle Tacoma Intl`). The existing goldens pin those numbers (3 455, 28 075), so this is
  recorded rather than changed; `gpsdb` and `airport::extract_airport_text` handle all three
  headers.
- **REA, second attempt, same result**: `analyze_function` on a 64-instruction routine timed out
  at 330 s. Ghidra driven directly with `-noanalysis` decompiles the same routine in seconds; see
  `tests/original_patch/re/README.md`.
